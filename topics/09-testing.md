# 09｜測試與可維護性

[回目錄](../README.md) · [快速複習](../quick-review.md)

## 1. 單元、整合與端到端測試

**白話與用途：** 單獨試煞車、把煞車裝到車上試、再整台車上路，是不同層級的驗證。測試讓變更有依據，降低回歸風險，但不同層級的速度、成本與能抓到的問題不同。

**實際場景：** 計價規則用單元測試，真實 SQL 與交易用整合測試，登入到下單的關鍵流程用端到端測試。

| 層級 | 著重 | 實際場景 |
| --- | --- | --- |
| 單元 | 小範圍邏輯，少外部依賴 | 折扣、狀態轉換、輸入邊界 |
| 整合 | 真正的元件互動 | SQL、交易、ORM 映射、API 與資料庫 |
| 端到端 | 完整使用流程 | 登入後下單並看到結果 |

**面試回答：**「單元測試驗邏輯，整合測試驗元件協作，端到端驗完整流程。我會讓大量快速測試守住核心規則，再用少量整合和端到端涵蓋真正的連接風險。」

**追問／易錯點：** 用記憶體假資料庫不保證真資料庫的 SQL、約束或併發行為相同。測試金字塔是成本提醒，不是固定比例；應依失敗風險安排。

## 2. 好測試、邊界案例與測試替身

**白話與用途：** 好測試像一張清楚的驗收單：給定什麼、做什麼、應該得到什麼。它驗證外部可觀察行為，而不是複製實作細節，讓內部重構仍有空間。

**實際場景：** 折扣門檻至少要測剛好低於、等於、高於；另外考慮空值、負值、重複與失敗。以下以常見的 xUnit 風格示意，專案不需安裝套件：

```csharp
using Xunit;

// 計價規則：滿 1000 打九折，負金額視為不合法。
public static class Pricing
{
    public static decimal CalculateTotal(decimal amount)
    {
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount));
        return amount >= 1000m ? amount * 0.9m : amount;
    }
}

public class PricingTests
{
    [Fact]
    public void Total_AppliesDiscountStartingAtThreshold()
    {
        // Arrange：準備；Act：執行；Assert：驗證。
        Assert.Equal(999m, Pricing.CalculateTotal(999m));
        Assert.Equal(900m, Pricing.CalculateTotal(1000m));
        Assert.Equal(900.9m, Pricing.CalculateTotal(1001m));
    }
}
```

在實際測試專案中需有 xUnit 相依；也應另驗證負金額會被拒絕。本筆記沒有新增套件。

**面試回答：**「我先找商業規則和容易出錯的邊界，讓測試可重複且不依賴執行順序。外部時間、網路或付款可用替身控制，但真正的整合風險仍用整合測試驗證。」

**追問／易錯點：** Stub 提供固定回答，Mock 常用來驗證互動，Fake 提供簡化但可運作的實作；不用拘泥名稱。過多驗證內部方法被呼叫幾次，會讓測試隨重構破碎。覆蓋率高不保證斷言有意義。

## 3. 例外處理與失敗邊界

**白話與用途：** 火警不能只關掉警報，必須知道誰負責處理。例外讓不正常的失敗傳到有能力處理的位置；不能靠空 catch 把問題當成功。

**實際場景：** 無庫存是可預期業務結果，可回傳明確失敗；資料庫連不上通常是系統錯誤，記錄後轉成一致的 API 錯誤。finally 放必要清理，資源可優先用 using。

```csharp
try
{
    await SaveAsync(token); // 假設此方法存在
}
catch (Exception ex)
{
    logger.LogError(ex, "儲存訂單失敗，OrderId={OrderId}", orderId);
    throw; // 保留原始堆疊；不是 throw ex;
}
```

**面試回答：**「我只在能處理或補充必要資訊的地方 catch，不吞掉失敗。預期的業務拒絕和系統例外分開，清理用 finally 或 using，對外回一致且不洩漏機密的錯誤。」

**追問／易錯點：** 這段記錄與重拋是示意，正式系統避免每層都重複記相同例外。取消不一定是系統故障。回應使用者失敗時，也要確認操作是否已部分完成。

## 4. DI、生命週期與合理分層

**白話與用途：** 廚師取得現成食材，不用每次自己種菜。Dependency Injection（相依性注入）把相依物件由外部提供，讓建立方式與使用邏輯分開，方便管理資源和替換有需要的相依。

**實際場景：** Web 邊界處理輸入與回應，應用邏輯負責流程，資料存取負責 SQL；不是每個小專案都要新增 Repository 或很多 Interface。即使用 DI，也能注入具體類別。

| .NET 常見生命週期 | 含義 | 要留意 |
| --- | --- | --- |
| Transient | 每次解析建立新實例 | 不代表每個請求只建立一次 |
| Scoped | 同一 scope 共用，Web 常是同一請求 | 不應被 Singleton 長期持有 |
| Singleton | 同一容器共用一個 | 共用可變狀態要考慮執行緒安全 |

**面試回答：**「DI 是從外部提供相依，降低邏輯與建立細節的耦合。分層用來管理責任，不是層越多越好；我會留意生命週期，例如 Singleton 不能直接長期抓著請求範圍的資料庫服務。」

**追問／易錯點：** ASP.NET Core 常見 DbContext 是 Scoped，通常不能讓同一實例同時執行多個資料庫操作。測試困難可能表示責任耦合，但不是遇到難測就把每個類別拆出 Interface。[Microsoft：DI 生命週期](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/overview#service-lifetimes)

## 5. Code Review 與除錯順序

**白話與用途：** Review 像另一個人檢查施工圖，重點是規則、風險和理解成本。除錯則是用證據逐步縮小範圍，不是一口氣改一堆可能相關的地方。

**實際場景：** Review 先看需求是否滿足、失敗／邊界與權限、資料一致性，再看可讀性；除錯先重現，讀實際請求、錯誤與日誌，確認在哪一層失敗，再用最小改動驗證。

**面試回答：**「我先確認可重現條件和實際資料，用日誌或斷點定位，再提出能被驗證的原因。修正後針對原問題與相關邊界驗證，不順便重構無關內容。」

**追問／易錯點：** 編譯成功只證明部分語法與型別檢查通過，不能證明 SQL、權限或併發正確。測試環境與正式環境的設定、版本、資料量差異也要查。

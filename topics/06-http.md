# 06｜HTTP、Web 與 API

## 1. 一次 Web 請求的旅程

**白話與用途：** 網址像店名，DNS 查出位置，網路連線把訊息送過去，HTTP 約定訊息怎麼表達。分清各層，才知道連不上、憑證錯誤與 API 回 500 是不同問題。

**實際場景：** 常見流程是 DNS 查位址 → 建立連線 → HTTPS 建立 TLS 保護 → 傳 HTTP 請求 → Proxy／Web Server／應用程式處理 → 回應。既有連線和 DNS 結果可能重用，不是每次都重跑。

常見 HTTP/1.1、HTTP/2 使用 TCP；HTTP/3 使用建於 UDP 上的 QUIC。TCP 提供可靠、有序的位元組流；UDP 不直接保證送達或順序，但上層協定可補上所需能力。

**面試回答：**「瀏覽器先透過 DNS 找位址，建立連線，HTTPS 再以 TLS 保護傳輸，接著送 HTTP 請求到後端。除錯時我會先區分 DNS、連線、TLS 和應用程式錯誤。」

**追問／易錯點：** HTTPS 保護傳輸機密性與完整性，並透過憑證等機制驗證伺服器；不會自動修好 SQL Injection 或權限漏洞。TCP 是串流，不能假設一次讀取就是一個完整訊息。

## 2. HTTP 方法、REST 與冪等性

**白話與用途：** HTTP 方法表達想對資源做什麼；REST 常用資源與一致的操作語意設計 API。冪等性是同樣操作重做多次，預期伺服器效果和做一次相同，能幫助安全處理重送。

| 方法 | 常見用途 | 語意 |
| --- | --- | --- |
| GET | 讀取 `/orders/42` | 安全、冪等，不應用來下單 |
| POST | 新增訂單或執行動作 | 不保證冪等 |
| PUT | 建立或完整替換指定資源 | 冪等 |
| PATCH | 部分更新 | 不保證冪等，取決於操作 |
| DELETE | 刪除指定資源 | 冪等 |

**實際場景：** DELETE 第一次回 204，第二次回 404，仍可能是冪等，因為資源都處於已不存在的狀態。PATCH 設定數量為 3 可以冪等，增加數量 1 則通常不是。[MDN：冪等性](https://developer.mozilla.org/en-US/docs/Glossary/Idempotent)

**面試回答：**「冪等是同樣操作重複執行，效果和一次相同，不要求每次回應完全相同。付款或下單遇到逾時可能已成功，所以不能直接盲目重送。」

**追問／易錯點：** 安全方法表示用戶沒有要求修改資源，不代表伺服器完全不能記錄日誌。HTTP 宣告語意不會替錯誤實作自動提供保障。POST 可透過冪等鍵設計安全重送：同一鍵與相同內容只完成一次；資料庫唯一約束、併發、處理中狀態與結果保存都要一起處理。

## 3. 狀態碼與 API 契約

**白話與用途：** 狀態碼像通知單上的處理結果，讓呼叫端知道成功、輸入有問題，還是服務失敗。清楚的契約包含輸入、輸出、錯誤與排序規則，讓前後端不必猜。

**實際場景：** 常用狀態碼：

| 狀態碼 | 用途 |
| --- | --- |
| 200／201／204 | 成功／已建立／成功但無回應內容 |
| 400 | 請求格式或參數錯誤 |
| 401／403 | 缺少有效身分驗證／伺服器拒絕存取，常見是權限不足 |
| 404／409 | 資源不存在／與目前狀態衝突，例如版本衝突 |
| 429 | 請求過多，需要限流 |
| 500／502／503／504 | 內部錯誤／Gateway 收到無效上游回應／暫時無法服務／Gateway 等上游逾時 |

**面試回答：**「API 要用適合的狀態碼，並提供一致、可理解的錯誤內容。401 常是身分驗證失敗，403 常是有身分但不能做這件事；錯誤回應不應直接暴露內部堆疊或機密。」

**追問／易錯點：** 分頁要有穩定排序和唯一欄位打破同值。Offset 深頁成本可能高，資料變動也可能重複或漏讀；Cursor 依最後讀到的排序鍵接續，但不方便直接跳任意頁。破壞性的欄位或語意修改需規劃版本與相容性。

## 4. Cookie、Session 與 JWT

**白話與用途：** HTTP 每個請求本身不會自動記得上次登入。Cookie 是瀏覽器儲存並依規則送出的資料；Session 常是伺服器存狀態、Cookie 帶查詢憑證；JWT 是可驗證的 token 格式，三者不是互斥方案。

**實際場景：** Session ID 可放 Cookie；JWT 也能放 Cookie 或 Authorization header。一般簽章 JWT 的 payload 可讀，簽章防竄改，不是加密。後端需驗證簽章、有效期、發行者與預期接收者等條件。

| 方式 | 常見取捨 |
| --- | --- |
| 伺服器端 Session | 容易撤銷；多台部署需共享或妥善管理狀態 |
| 簽章 JWT | 各服務可驗證 token；即時撤銷需額外機制，不能只刪掉前端副本 |

**面試回答：**「Cookie 是傳遞與儲存機制，Session 是狀態管理方式，JWT 是 token 格式。JWT 通常是簽章不是加密；選擇時要考慮撤銷、保存位置與多台服務的需求。」

**追問／易錯點：** Cookie 的 Secure 限制 HTTPS 傳送，HttpOnly 限制 JavaScript 直接讀取，SameSite 控制部分跨站傳送；這些是不同保護。[MDN：Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)

## 5. 同源政策與 CORS

**白話與用途：** 瀏覽器不讓一個網站隨便讀另一個網站的資料。同源通常看協定、主機與連接埠；CORS 是伺服器告訴瀏覽器哪些跨來源存取可被允許，方便合法的前後端分站部署。

**實際場景：** 前端在 `https://app.example.com`，API 在 `https://api.example.com`，是不同來源。某些請求會先送 OPTIONS 預檢；簡單請求可能直接送出，再決定是否讓 JavaScript 讀到回應。

**面試回答：**「CORS 是瀏覽器的跨來源讀取控制。後端設定允許來源、方法與標頭；它不是使用者授權，非瀏覽器客戶端也不受同樣限制。」

**追問／易錯點：** Cookie 等憑證跨來源傳送要配合瀏覽器與伺服器設定，帶憑證時不能用萬用來源 `*`。來源被擋不代表請求一定沒送到後端，更不能把 CORS 當 CSRF 防護。[MDN：CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)

## 6. HTTP 快取與條件請求

**白話與用途：** 瀏覽器或中介伺服器可以保存回應，減少重複下載。HTTP 快取靠回應標頭表達能否保存、多久算新鮮，以及過期後如何確認內容有沒有變。

**實際場景：** `Cache-Control: max-age=60` 表示新鮮期限；有 ETag 時，客戶端可帶 `If-None-Match` 再驗證，內容未變可回 304，省掉回應本文的傳輸。

**面試回答：**「HTTP 快取減少重複請求或下載。Cache-Control 管保存與新鮮度，ETag 配合條件請求確認版本；個人資料要避免被共享快取錯誤提供給別人。」

**追問／易錯點：** `no-cache` 不是禁止保存，而是重用前需再驗證；`no-store` 才是要求不要保存。`private` 限制共享快取保存，但不是加密。[MDN：HTTP 快取](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)

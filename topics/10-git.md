# 10｜Git 與協作流程

[回目錄](../README.md) · [快速複習](../quick-review.md)

## 1. 工作區、暫存區與 Commit

**白話與用途：** 工作區像正在寫的草稿，暫存區像挑好要交出去的頁面，Commit 是把這批內容與說明存成一個版本。分開管理能讓每次提交聚焦同一目的。

**實際場景：** 同一檔案同時有修 bug 和未完成調整，可分區塊暫存，不必全部一起提交。

```bash
git status
git diff                 # 工作區相對暫存區的變更
git add -p               # 逐區塊挑選；新增檔案需另外 add
git diff --staged        # 這次 commit 真正會包含的內容
git commit -m "修正訂單金額驗證"
```

**面試回答：**「工作區是目前檔案，暫存區是準備提交的內容，commit 是一個版本快照。我會先檢查 staged diff，讓提交只包含同一目的，方便 review 和回復。」

**追問／易錯點：** add 後再改檔案，新改動不會自動進入已暫存內容。Commit 在本機，Push 才把本機提交送到遠端；`.gitignore` 不會自動停止追蹤已提交檔案。

## 2. Branch、Merge、Rebase 與 Fetch

**白話與用途：** 分支像在某個版本上開出工作路線，本質是指向提交的可移動參考。Merge 保留分岔歷史再整合；Rebase 把提交重新套在新的基底上，讓歷史較直，但會產生新的提交身分。

**實際場景：** 自己尚未共享的分支可以 rebase 整理；多人共同使用的分支，重寫歷史會增加協作成本，需先有明確共識。

| 操作 | 意義 |
| --- | --- |
| fetch | 取得遠端資訊與物件，更新遠端追蹤參考，不直接整合目前分支 |
| merge | 整合歷史；可能 fast-forward，也可能建立 merge commit |
| rebase | 重新套用提交，改變相關 commit ID |
| pull | 先 fetch，再依設定 merge 或 rebase |

**面試回答：**「Merge 整合分支並保留分岔脈絡，Rebase 重新套提交讓歷史較直，但會改 commit ID。自己的未共享分支可整理，大家已依賴的歷史不要隨意重寫。」

**追問／易錯點：** Merge 不一定產生新 merge commit，能直接前進時可 fast-forward。`push --force-with-lease` 比無條件 force 多了檢查，但仍是重寫遠端，不能替代團隊溝通。

## 3. 衝突與 Cherry-pick

**白話與用途：** 兩個人改同一段文字，工具無法判斷要哪個版本，需要人確認最終規則。衝突是整合時需做的決策，不只是移除標記。

**實際場景：** Merge 或 Rebase 出現衝突，先讀共同基底與兩邊需求，再編輯最終內容，add 後繼續相應流程。Cherry-pick 把指定提交的變更套到另一分支，適合搬一個獨立修正。

**面試回答：**「遇到衝突我先理解兩邊想解決的問題，再整合內容，不能只選 ours 或 theirs。處理完還會檢查相關功能，因為文字不衝突也可能有邏輯衝突。」

**追問／易錯點：** Rebase 中 ours／theirs 的角色可能和直覺不同，別盲選。Cherry-pick 通常產生新的 commit ID，也可能依賴前面未搬過來的修改。想撤銷尚未完成的整合可用對應 `merge --abort`／`rebase --abort`，但要留意原本未提交修改。

## 4. Restore、Reset 與 Revert

**白話與用途：** 丟掉草稿、把版本指標往回移、再補一份更正紀錄，是不同操作。分清楚才能避免丟失修改或破壞別人使用的歷史。

| 操作 | 用途 | 風險 |
| --- | --- | --- |
| restore | 還原檔案內容或取消暫存 | 還原工作區可丟掉未提交修改 |
| reset | 移動目前分支指標，也可調整暫存區／工作區 | `--hard` 會捨棄受影響的已追蹤未提交修改 |
| revert | 新增一個反向提交，撤銷指定變更 | 不改寫既有歷史，但可能衝突 |

**實際場景：** 公開分支的錯誤提交通常用 `git revert <commit>`，保留協作歷史；只想取消暫存而保留檔案可用 `git restore --staged <file>`。[Git：revert](https://git-scm.com/docs/git-revert)

**面試回答：**「Restore 處理檔案或暫存內容，Reset 主要調整版本指標並依模式改內容，Revert 新增反向提交。已共享的錯誤通常用 Revert，避免讓其他人的歷史失去基底。」

**追問／易錯點：** soft reset 保留暫存內容，mixed 重設暫存但保留工作區，hard 也重設工作區。Reflog 可協助找到曾指向的提交，但不是所有未提交檔案的備份。機密即使用 revert 仍留在歷史，應先撤銷或輪替。

## 5. CI/CD 與部署風險

**白話與用途：** CI 像每次交稿都自動檢查能否拼成完整作品；CD 把產物可靠地交付到環境。持續交付通常仍保留部署批准，持續部署則讓通過流程的修改自動上線。

**實際場景：** PR 執行還原相依、編譯與必要測試，產出可辨識版本，再部署到測試或正式環境。部署後檢查健康、錯誤率與關鍵流程，不能把「pipeline 綠燈」當作正式環境一定正常。

**面試回答：**「CI 自動驗證整合，CD 讓交付與部署可重複。流程除了 build 和 test，還要管理設定、機密、版本、部署後驗證與回復方式。」

**追問／易錯點：** 資料庫 migration 可能讓舊版程式無法運作，回復程式不等於能直接回復資料。結構變更要考慮相容性、備份和部署順序；不必為小專案先建最複雜的部署平台。

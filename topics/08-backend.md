# 08｜後端可靠性與效能

[回目錄](../README.md) · [快速複習](../quick-review.md)

## 1. 快取與一致性

**白話與用途：** 快取像把常看的答案放在桌上，避免每次回倉庫重查，換取更低延遲與較少來源負載。代價是答案可能過期，還要花記憶體並處理失效。

**實際場景：** 常見 Cache-aside：讀取先查快取，沒有才查資料庫並寫回；修改成功後刪除或更新相關快取，再配合 TTL 控制保存時間。

**面試回答：**「快取用額外儲存換速度和來源負載，但要接受或處理過期資料。我會先問資料能舊多久，再決定快取鍵、TTL 和更新失效方式。」

**追問／易錯點：** 刪快取後，較早開始的讀取仍可能把舊資料寫回，所以『寫資料庫再刪快取』不是絕對強一致。熱點同時過期可用合併同鍵查詢、限制回源或分散 TTL；也要設容量上限。個人資料快取要含使用者／租戶範圍，不能讓不同人共用錯誤結果。快取不可作為庫存或付款正確性的唯一依據。

## 2. 逾時、重試與冪等

**白話與用途：** 叫不到車不能永遠等，但再叫一次可能來兩台。逾時限制等待成本；重試應對暫時故障，但可能重複產生副作用，還會增加負載。

**實際場景：** 查詢外部 API 可對合適的短暫失敗有限重試，採退避與隨機延遲，避免大家一起重送。付款逾時卻可能已扣款，要用穩定冪等鍵、結果查詢與對帳確認，而非直接建立新付款。

**面試回答：**「逾時只代表我沒等到結果，不代表對方沒成功。重試要確認操作能安全重做，限制次數和總時間，採退避；輸入或權限錯誤通常重試也沒用。」

**追問／易錯點：** 多層各自重試會把流量放大。外部服務持續故障時，可限流、限制併發或用斷路器暫停呼叫，避免拖垮本服務。429 應尊重重試提示；降級只能在業務允許下使用，不能把未完成付款假裝成功。

## 3. 背景工作、訊息佇列與至少一次投遞

**白話與用途：** 下單時先完成必要資料，再把寄信工作交給待辦箱，讓客戶不用一直等。背景處理降低請求等待，也能緩衝尖峰；代價是要追蹤工作狀態、重試與失敗。

**實際場景：** 寄通知、產報表、匯出檔案適合背景工作。重要工作要存到可恢復的儲存或可靠佇列，不能只在請求中丟一個無人追蹤的 Task。

**面試回答：**「背景工作把不必即時完成的事情移到請求之外。訊息可能重送，所以消費端要能冪等處理，成功後才確認；多次失敗要能留下可檢查、可補救的紀錄。」

**追問／易錯點：** DB 已提交、訊息卻沒送出，是跨系統寫入的落差。必要時可在同一 DB 交易寫入訂單與待送事件，再由背景工作投遞（Outbox）；仍需處理重送。只是小型非關鍵任務時，先用簡單背景工作即可，不必直接導入大型訊息平台。「恰好一次」不能只靠一句產品保證涵蓋所有外部副作用。

## 4. 無狀態服務、共享狀態與負載平衡

**白話與用途：** 多個櫃台能分流，但下一次不一定排到同一個人。負載平衡分配請求；無狀態服務避免把下一次必需的資料只放在某台主機記憶體，讓擴充與故障切換較容易。

**實際場景：** 部署兩台 API，Session、重要工作狀態或檔案若只存在其中一台，另一台可能找不到。可使用共享 Session、資料庫或物件儲存；部署方案仍依實際規模選擇。

**面試回答：**「無狀態是請求不依賴某台主機保存的對話狀態，不是整個系統沒有資料。多台 API 共用必要狀態，負載平衡才能比較容易分流和切換。」

**追問／易錯點：** Sticky Session 能暫時固定路由，但故障與擴容仍要處理。加 API 主機不會自動解決共用資料庫瓶頸，C# lock 也不會因此變成跨主機鎖。

## 5. 效能量測、日誌與可觀測性

**白話與用途：** 只知道『很慢』像只知道病人不舒服，還不知道哪裡出問題。Log 記事件，Metric 看整體數字與趨勢，Trace 串起一次請求跨服務的路徑，能幫助定位原因。

**實際場景：** API 延遲上升：先查受影響範圍與最近部署，再分解 DB、外部 HTTP、CPU、GC、鎖等待與連線池。以 trace／request ID 串接紀錄；記耗時與必要識別資訊，遮蔽機密。

**面試回答：**「我會先量測瓶頸，不直接猜。Log 看個別事件，Metric 看延遲和錯誤率趨勢，Trace 看一次請求各段耗時，定位後再決定索引、快取或其他修正。」

**追問／易錯點：** 平均延遲會掩蓋慢請求，p95 表示約 95% 的觀測請求不超過該延遲；吞吐量和單次延遲是不同指標。也要觀察錯誤率、資源飽和與流量，不只看 CPU。最佳化後用相近條件比較，確認瓶頸沒有只是移到別處。
